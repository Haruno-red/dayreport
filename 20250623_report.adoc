= AnsibleによるInfrastructure as Code

== IaC（Infrastructure as Code）とは
* 手作業で行っていたインフラ構築を、コード（定義ファイル、コマンド等）を使用して行う方法。
* 構築やメンテナンス等の作業をコードで記述、実行することでインフラ構築作業を行う。
* コードの記述や実行に使用するツールは複数存在し、ツールごとに実現可能な作業内容が異なるため、特徴を理解し最適なものを選択することが大切。

== Ansibleの仕組み

. Ansibleの重要用語
.. *インベントリ* : ターゲットの情報（ホスト名、IPアドレス等）が記述されたファイル
.. *Playbook* : メンテナンス内容（ソフトウェアの追加/変更/削除）が記述されたファイル
.. *冪等性* : 同じ操作を何度繰り返しても、同じ結果が得られるという性質
.. *モジュール* : ネットワーク、クラウド管理等、様々なユースケースに対するIT機能を実行できる要素
.. *ロール* : Ansibleで実行されるタスクを整理するための仕組み（タスク分割による単位分け）

. Ansibleが実行されるステップ
.. インベントリを元に、どのターゲットに対してメンテナンスを行うか、取得する。
.. Playbookを元に、ターゲットに対して行うメンテナンス内容を取得する。
.. 各ターゲットに対してメンテナンスを行う。（ハードウェアに対しては、変更はできず、情報取得のみ実行可能。）

== インベントリの種類

[option="header"]
|======
|種類　|概要
|Hostsファイル　|ホスト名をIPアドレスにマップするために使用するプレーンファイル（拡張子無し） +
DNSサーバを使用せずに名前解決するために使用される +
インベントリファイルが定義されないときに使用される「デフォルトインベントリ」である
|インベントリファイル　|Ansibleでターゲットを管理するためのファイル（拡張子は任意） +
Hostsファイルより柔軟にターゲットを管理できる
|======

. Yaml構成要素の理解

[cols="5,5a", option="header"]
|======
|構成要素　|表現方法
|リスト　|[source,yaml]
----
- A
- B
- C
----
（要素の列挙）
|ディクショナリー　|[source,yaml]
----
A: aa
B: bb
C: cc
----
（キー: 値 形式）
|リストとディクショナリーの組み合わせ　|[source,yaml]
----
- A: aa
- B: bb
- C: cc
----
（キー: 値 形式で要素を列挙）
|グループ化　|＜リスト＞ +
[source,yaml]
----

  - A
  - B
  - C
----
＜ディクショナリー＞ +
[source,yaml]
----

  - A: aa
  - B: bb
  - C: cc

|======

. Playbookの作法の理解
+
[option="header"]
|======
|作法　|概要
|サマリ部の記述　|Playbookの概要定義（簡潔なメンテナンス内容の記述） +
メンテナンス対象のターゲットの定義（インベントリの参照）
|タスク部の記述　|メンテナンス内容の定義 +
タスク（メンテナンスの単位）の定義 +
タスクに使用するモジュールの定義
|構成要素のグループ化　|「name」というキーの使用
|======

. Yaml文法の最低限覚えておきたい８か条
+
[option=""header]
|======
|No　|概要
|1　|リストはハイフン（ `-` ）を使用します。
|2　|ディクショナリーはキーと値をコロン（ `:` ）で区切ります。
|3　|ラベル付けは半角スペース２つのインデントを使用します。
|4　|コメントはハッシュ（ `#` ）を使用します。
|5　|文字列はクォート（ `"` または `'` ）で囲みます。
|6　|真偽値は `True` または `False` を使用します。
|7　|特殊文字はエスケープシーケンスを使用します。
|8　|文字列が複数行になる際はパイプまたは大なり（ `>` ）を使用します。
|======

== モジュールの概要

. モジュールの種類
+
[option="header"]
|======
|種類　|概要
|標準モジュール　|Ansibleに標準で搭載されているモジュールでインストール後、即利用できる。 +
現在では4000以上の標準モジュールが搭載されている。 +
メンテナンス内容に応じて使用するモジュールを選定してタスクを定義する。
|カスタムモジュール　|様々なプログラミング言語を用いてユーザが独自に作成し、利用できる。 +
内部的にPythonを使用しているため、Pythonでの作成が推奨されている。 +
複雑なメンテナンス等で、タスクに組み込む用途で使用される。
|======

. カスタムモジュールの利用の流れ
.. *カスタムモジュールの作成* …  複雑なメンテナンス内容をコードで記述する。 +
.. *Ansibleの設定ファイル修正* …  インベントリの配置先パス等を修正し、カスタムモジュールの配置先や必要なライブラリの配置先を定義する。 +
.. *カスタムモジュールの配置* …  設定ファイルで定義した配置先にカスタムモジュールを配置する。 +
.. *Playbookの作成* …  カスタムモジュール名の定義でタスクにカスタムモジュールを組み込む。 +
.. *Playbookの実行* …  ターゲットに対してカスタムモジュールを使用した複雑なメンテナンスが行われる。 

== ロール作成の手順

. *タスク分割基準の決定* : プロジェクトで重視するポイントに応じて基準を決定する。
+
[option=""header]
|======
|基準　|内容
|リソースの種類　|各ソフトウェアのリソースに関連するタスクごとに分けて管理する
|操作の種類　|各タスクの役割ごとに分けて管理する
|======

. *タスク分割&ロール名付与* : 既存のPlaybookからタスク分割し、実行するロール名を付与する。（新しいファイルの作成）
. *各ロールの呼び出し処理記述* : 各ロールを呼び出すためのメインPlaybookを作成する。（既存のPlaybookの書き換えも可）

== 出力結果の見方

[cols="2,7a", options="header"]
|======
|セクション　|概要
|PLAY　|Playbookを実行したターゲットを出力 +
※ターゲット指定に誤りがないか要確認 +
|TASK　|Playbook内の各タスクで、タスク名とその実行結果を出力 +
[options="header"]
!====
!ステータス　!内容
!ok　!正常に終了した（ターゲットに変化無し）
!changed　!正常に終了した（ターゲットに変化有り）
!skipped　!タスクを実行しなかった
!failed　!エラーが発生した
!====
|PLAY RECAP　|タスク実行結果のサマリを出力 +
[options="header"]
!====
!ステータス　!内容
!ok　!正常に終了したタスク数
!changed　!正常に終了したタスクのうち、ターゲットの状態が変化したタスク数
!unreachable　!通信エラー起因で、エラーが発生したタスク数
!failed　!通信エラー起因以外で、エラーが発生したタスク数
!skipped　!タスクを実行しなかったタスク数（処理条件が決まっている場合等）
!rescured　!rescureディレクティブ（途中でエラーが発生しても特定のタスクを実行するように +
指示）を実行したタスク数
!ignored　!エラーが発生したが無視したタスク数（あるタスクに対してエラーが発生しても無視 +
するように指示できる）
!====
|======
